# Dolina Coffee

Программа лояльности сети кофеен **Dolina Coffee**: PWA для гостя, API поверх iiko и админ-панель для менеджеров.

**Прод:** https://dolina-coffee.ru · **Админка:** https://dolina-coffee.ru/admin/

Учёт бонусов — на стороне **iiko** (iikoCloud API). Приложение не источник истины по баллам: их считает касса (iikoCard), приложение показывает баланс/QR и инициирует операции.

## Из чего состоит

| Модуль | Папка | Стек | Что это |
|---|---|---|---|
| **PWA гостя** | `src/` | React 18 · TypeScript · Vite 6 · Tailwind 4 · VK ID SDK | Карта лояльности: вход через VK ID, QR, баланс, история, дистанционный заказ |
| **Backend** | `server/` | Node 20 · Express 4 · TypeScript · SQLite (better-sqlite3) | Прокси к iiko, журнал операций, вебхуки, аналитика, OLAP-отчёты |
| **Админ-панель** | `admin/` | React 18 · TypeScript · Vite 6 · Tailwind 4 | Задания менеджерам, недельная аналитика, отчёты |

Три независимых npm-проекта со своими `package.json` и деплоем.

## Архитектура

```
┌───────────────────────┐   VK ID (scope: phone)    ┌──────────────┐
│   PWA гостя (src/)     │ ────────────────────────▶ │   VK ID      │
│  React · TS · Tailwind │ ◀── code + device_id ──── │  OAuth/PKCE  │
└───────────┬───────────┘                            └──────────────┘
            │ HTTPS /api  (same-origin, nginx)
            ▼
┌───────────────────────┐   customer/info, wallets  ┌──────────────┐
│   Backend (server/)    │ ────────────────────────▶ │ iikoCloud API│
│  Express · TS          │ ◀── баланс, карта ─────── │ api-ru.iiko  │
│  • прокси к iiko       │                           │  .services   │
│  • журнал операций     │   вебхуки закрытых чеков  └──────────────┘
│  • SQLite аналитика    │ ◀──────────────────────────────┘
│  • OLAP-отчёты         │ ────────────────────────▶ ┌──────────────┐
└───────────┬───────────┘   /resto/api (OLAP)        │ iikoServer   │
            │ /api/admin                             │  офиса       │
            ▼                                        └──────────────┘
┌───────────────────────┐
│  Админка (admin/)      │
│  задания · аналитика   │
└───────────────────────┘
```

**Почему backend обязателен:** обмен VK `code → access_token → phone` и `apiLogin` iiko нельзя держать в браузере, а историю операций iikoCloud отдельным методом не отдаёт — её собираем сами из вебхуков и храним у себя.

## Функционал

### PWA гостя

**Авторизация.** Вход через VK ID в один тап (OneTap, PKCE — секрет в браузере не нужен). VK возвращает `code + device_id`, бэкенд меняет их на номер телефона (scope `phone`), по номеру ищется карта в iiko. Регистрация карты происходит офлайн на кассе — приложение её не создаёт: незарегистрированный гость видит экран «прийдите в кофейню».

**Карта лояльности.** Главный экран: QR-код (в него зашит трек карты — кассир сканирует в iikoFront), баланс бонусов, размер кэшбека, условия программы. Вёрстка адаптируется по высоте: QR остаётся квадратным и не выходит за экран на коротких дисплеях.

**Уровни лояльности:**

| Статус | Условие | Обводка аватара |
|---|---|---|
| **СТАНДАРТ** | базовый, есть у всех | серебряная |
| **ПРЕТЕНДЕНТ НА ПРО** | 7 визитов за последние 30 дней; действует до конца текущего месяца и весь следующий | бронзовая |
| **ПРО** | категория с кэшбеком 15% в лояльности iiko; перманентный | золотая |

В момент, когда гость впервые набирает 7 визитов, один раз показывается модал: статус уже есть, но за ПРО нужно прийти в кофейню — категорию ставят на кассе.

**Профиль.** История начислений и списаний из собственного журнала операций.

**Дистанционный заказ (панель 🔥).** Любимые позиции гостя сверху, ниже меню по категориям, корзина внизу. Работает через внешнее меню iiko. Реальное создание заказа включается флагом `ORDER_LIVE`; пока онлайн-оплата не настроена — режим заглушки.

**PWA.** Манифест + иконки, ставится на домашний экран и работает как приложение.

### Админ-панель

**Задания.** Система сама находит гостей «под риском» и ставит менеджеру задачи на звонок. Ключевая идея в `cadence.ts`: сравнивается не «эта неделя против прошлой» (у нерегулярного гостя 3→2 — это шум, регрессия к среднему), а насколько долго гость молчит относительно **своего обычного** интервала между визитами. К задаче прикладываются любимый напиток и блюдо гостя — чтобы было с чем звонить.

**Аналитика.** Гости, чеки и средний чек по сегментам частоты визитов (`7+, 6, 5, 4, 3, 2, 1`), по 6 недель на график: текущая неделя выделена, пять прошлых серые. Выбор недели — барабаном-колесом; недели без данных и будущие недоступны.

**Отчёты.** Произвольные OLAP-отчёты iikoServer с выбором колонок; из отчёта «кто что купил» автоматически формируются любимые позиции гостей.

**Выгрузки.** Аналитика, задания и лиды в `.xlsx`.

**Доступ.** Логин/пароль (bcrypt) → JWT, роли `admin` и `manager`. Первый админ сидируется из ENV при старте.

### Backend

**Две авторизации в iiko.** `iikoClient.ts` поддерживает оба флоу и выбирает по наличию переменных: v1 — обычный ресторанный ключ (`POST /api/1/access_token`), v2 — partner/marketplace (`POST /api/v2/access_token`). Токен кэшируется на ~час и обновляется сам.

**Журнал операций.** iikoCloud не отдаёт историю транзакций, поэтому ведётся своя: наполняется вебхуками iiko и собственными вызовами `topup`/`chargeoff`. Хранилище — JSON-файл на Docker-volume.

**Сбор истории.** Вебхуки копят данные только вперёд, а список заказов POS через Transport API недоступен. Поэтому история заливается импортом «Журнала операций» из iikoWeb (`.xlsx`). Гость оттуда известен только по телефону и кладётся под синтетическим ключом `phone:+7XXXXXXXXXX`; настоящий `iikoId` приезжает позже — с вебхуком закрытия чека или при входе гостя в приложение, и `identity.ts` сводит записи.

**Свежесть данных.** Push-вебхуки iiko ненадёжны, поэтому каждую ночь в 03:15 крон подтягивает чеки известных гостей за 2 недели и пересчитывает недели окна. Пул щадящий — резкий всплеск запросов приводит к бану IP на стороне iiko.

## API

### Публичный — `/api`

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` |проверка живости сервиса |
| `GET` | `/venue` | точка кофейни (адрес, координаты) |
| `GET` | `/menu` | внешнее меню iiko |
| `GET` | `/customer` | гость по телефону: карта, баланс, кошельки |
| `GET` | `/customer/:id/transactions` | история операций из журнала |
| `GET` | `/customer/:id/favorites` | любимые позиции |
| `GET` | `/customer/:id/qr` | PNG QR-кода карты |
| `POST` | `/customer/:id/contender-seen` | отметить показ модала «претендент» |
| `POST` | `/order` | дистанционный заказ |
| `POST` | `/wallet/topup` · `/wallet/chargeoff` | начисление / списание бонусов |
| `POST` | `/webhooks/iiko` | приём вебхуков iiko (закрытые чеки) |

### Админка — `/api/admin`

| Группа | Endpoints |
|---|---|
| Доступ | `POST /login` · `GET /me` · `POST /users` |
| Недели и аналитика | `GET /weeks` · `GET /analytics` · `POST /weeks/:week/confirm` |
| Задания | `GET /tasks` · `POST /tasks/:id/done` |
| Данные | `POST /backfill` · `POST /refresh` · `POST /rebuild` · `POST /import-journal` · `POST /nomenclature/refresh` |
| Отчёты | `GET /report` · `GET /olap/status` · `GET /olap/columns` · `POST /olap/report` |
| Выгрузки | `GET /export/analytics.xlsx` · `/export/tasks.xlsx` · `/export/leads.xlsx` |
| Сегменты | `GET /segment1` · `POST /segment1` |

## Модель данных

SQLite, схема создаётся идемпотентно при старте (`server/src/admin/db.ts`):

| Таблица | Содержит |
|---|---|
| `users` | пользователи админки (логин, bcrypt-хеш, роль) |
| `guests` | гости: `iikoId` либо синтетический `phone:+7…`, телефон, имя |
| `orders_daily` | агрегат чеков гостя за день |
| `processed_orders` | идемпотентность приёма вебхуков |
| `week_guest` | снимок гостя за неделю: `visits30d`, чеки, сумма, сегмент 1..7 |
| `week_segment` | агрегат по сегменту за неделю (для графиков) |
| `week_status` | состояние недели (подтверждена менеджером) |
| `tasks` | задания менеджерам с причиной |
| `guest_items` | позиции гостя — источник «любимого» |
| `guest_loyalty` | уровень лояльности и кэшбек из iiko |
| `nomenclature` | кэш номенклатуры iiko (категория напиток/блюдо) |

## Запуск локально

```bash
# 1. Backend
cd server
npm install
cp ../.env.example .env      # заполнить ключи iiko
npm run dev                  # tsx watch → :3001

# 2. PWA гостя
npm install
npm run dev                  # vite → :5173

# 3. Админ-панель
cd admin
npm install
npm run dev
```

Фронт без `VITE_API_BASE` работает на мок-слое (`src/services/mockData.ts`) — экраны можно разрабатывать без бэкенда. Чтобы бить в прод-API: `VITE_API_BASE=https://dolina-coffee.ru`.

**Dev-превью статусов** (только в `DEV`): `#standard`, `#contender`, `#pro` — подменяют гостя; `#profile` открывает профиль сразу.

## Переменные окружения

Все секреты — только в `.env`, шаблон в `.env.example`.

**iiko Cloud**
`IIKO_API_BASE` · `IIKO_API_LOGIN` (v1) · `IIKO_API_KEY`, `IIKO_CLIENT_SECRET`, `IIKO_APP_ID` (v2) · `IIKO_ORGANIZATION_ID` · `IIKO_WEBHOOK_SECRET`

**Дистанционный заказ**
`IIKO_EXTERNAL_MENU_ID` · `IIKO_TERMINAL_GROUP_ID` · `IIKO_ORDER_SOURCE_KEY` · `ORDER_LIVE` (`1` — создавать реальные заказы)

**iikoServer / OLAP** — пусто = страница отчётов в заглушке
`IIKO_RESTO_HOST` · `IIKO_RESTO_LOGIN` · `IIKO_RESTO_PASS` либо `IIKO_RESTO_PASS_SHA1`

**Админка**
`ADMIN_JWT_SECRET` (обязательно на проде) · `ADMIN_SEED_LOGIN` · `ADMIN_SEED_PASSWORD` · `ADMIN_DB_PATH`

**Точка и инфраструктура**
`VENUE_NAME` · `VENUE_ADDRESS` · `VENUE_LAT` · `VENUE_LON` · `PORT` · `CORS_ORIGIN` · `JOURNAL_PATH`

## Деплой

Сервер `72.56.9.4`, Docker + nginx, доступ по ssh-ключу `~/.ssh/fantasy_dev`.

```bash
./deploy.sh          # PWA: сборка образа linux/amd64 → перенос → рестарт контейнера
./deploy-api.sh      # backend: исходники на сервер, сборка ТАМ (нативный better-sqlite3)
./deploy-admin.sh    # админка: npm run build → статика в /opt/dolina/admin-dist
```

Backend собирается на сервере намеренно: у `better-sqlite3` нативный модуль, а Docker Hub отдаёт 429 — обходится локальным тегом `node:20-slim-amd64`.
